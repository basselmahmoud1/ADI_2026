## 1. Project Overview

This project implements a **cocotb-based testbench** for the same 4-bit ALU used in the SystemVerilog class-based environment.  
Cocotb allows writing testbenches entirely in **Python** while co-simulating with any standard HDL simulator.

The testbench implements a layered architecture in Python:

- **`Driver`** — Sends stimulus transactions to the DUT via the cocotb handle
- **`Monitor`** — Samples DUT inputs and outputs, assembles `Transaction` objects
- **`Scoreboard`** — Validates DUT results against a Python reference model
- **`Transaction`** — Data class representing one ALU operation and its result

Waveform dumping is handled by the `dump.v` Verilog module which generates a **VCD** (Value Change Dump) file viewable in GTKWave.

## 2. DUT Description

**Module:** `ALU` (defined in `ALU.sv`, package in `ALU_pkg.sv`)  
**Parameter:** `WIDTH = 4` (default 4-bit)

| Port | Direction | Width | Description |
|------|-----------|-------|-------------|
| `clk` | Input | 1 | System clock |
| `rst` | Input | 1 | Synchronous active-high reset |
| `a` | Input | 4 | Operand A (signed) |
| `b` | Input | 4 | Operand B (signed) |
| `op_code` | Input | 2 | Operation select |
| `result` | Output | 4 | ALU result (signed, registered) |
| `z` | Output | 1 | Zero flag |
| `n` | Output | 1 | Negative flag |
| `c` | Output | 1 | Carry flag |
| `v` | Output | 1 | Overflow flag |

## 3. Testbench Architecture

```
test.py (Python)
+-------------------+
|   ALU_test()      |  <-- @cocotb.test() coroutine
|                   |
|  +-----------+    |       Cocotb Bridge
|  |  Driver   |----+----> dut.a / dut.b / dut.op_code / dut.rst
|  +-----------+    |
|                   |
|  +-----------+    |
|  |  Monitor  |----+----> reads dut signals on each clock edge
|  +-----------+    |
|       |           |
|  +-----------+    |
|  |Scoreboard |    |  <-- compares DUT output vs. Python reference model
|  +-----------+    |
+-------------------+
         |
         v
   [ Icarus Verilog ]
   ALU.sv + ALU_pkg.sv
         |
         v
   dump.v -> waveform.vcd  (VCD waveform file)
```

**Clock:** 10 ns period (100 MHz), generated by cocotb's `Clock` utility.  
**Communication:** Python `Queue` objects (from `cocotb.queue`) are used as internal mailboxes between Driver, Monitor, and Scoreboard.


**Step 2: Run the testbench using `make`**

```bash

```

This single command does everything:

| What happens | Description |
|-------------|-------------|
| Reads the `Makefile` | Picks up simulator, sources, and module names |
| Compiles `ALU_pkg.sv`, `ALU.sv`, `dump.v` | Uses `iverilog` to elaborate the design |
| Links cocotb with Icarus Verilog | Cocotb injects the Python TB into the simulation |
| Runs `test.py::ALU_test` | Executes all test cases in the Python testbench |
| Generates `waveform.vcd` | Produced by the `dump` module alongside simulation |
| Generates `results.xml` | JUnit-format test result report |

---

**Step 3: Inspect the terminal output**

A successful run looks like this:

```
     0.00ns INFO     cocotb.gpi                         ..._init.py:...  Running on Icarus ...
    ...
    20.00ns INFO     cocotb.ALU                         test.py:57   RESET_DONE
    30.00ns INFO     cocotb.ALU                         test.py:118  Monitor: Transaction(a=3, b=2, op=ADD, ...)
    ...
    INFO     cocotb.ALU                         test.py:151  Scoreboard: Transaction Passed
    ...

```

If any assertion fails in the Scoreboard, cocotb will print the mismatch and mark the test as `FAILED`.


This removes `sim_build/`, `results.xml`, `__pycache__/`, and other generated files (but **not** `waveform.vcd`).  
Then run `make` again for a fresh build.

## 7. How to Generate & View the Waveform

### How the VCD is Generated

The `dump.v` module is compiled alongside `ALU.sv` and is specified as an additional top-level elaboration target in the `Makefile` via:

```makefile
COMPILE_ARGS = -s dump
```

At the start of simulation, the `dump` module executes:

```verilog
module dump;
    initial begin
        $dumpfile("waveform.vcd");   // output file name
        $dumpvars(0, ALU);           // dump ALL signals inside the ALU module
    end
endmodule
```

This tells Icarus Verilog to record every signal transition inside the `ALU` module to `waveform.vcd` starting from time 0.

The file is written automatically — **no extra steps needed** beyond running `make`.

---

### Viewing the Waveform in GTKWave

**Step 1: Confirm `waveform.vcd` was generated**

After running `make`, check that the file exists:

```bash
# Linux/macOS/WSL
ls -lh waveform.vcd

# Windows PowerShell
Get-Item waveform.vcd
```

---

**Step 2: Open GTKWave**

```bash
gtkwave waveform.vcd
```

> On Windows, you can also double-click `waveform.vcd` if GTKWave is registered as the default VCD viewer.

---

**Step 3: Add signals to the waveform viewer**

Once GTKWave is open:

1. In the **Signal Search Tree** (left panel), expand the `ALU` scope
2. Select the signals you want to view:
   - `clk` — Clock
   - `rst` — Reset
   - `a` — Operand A
   - `b` — Operand B
   - `op_code` — Operation select
   - `result` — ALU result
   - `z`, `n`, `c`, `v` — Status flags
3. Click **Append** (or drag) to add them to the waveform window
4. Press `Ctrl+Shift+F` (or use **View → Zoom to Fit**) to fit the full simulation in view

---

**Step 4: Change signal radix for readability (optional)**

To view `a`, `b`, `result` as **signed decimal** instead of binary:

1. Right-click the signal name in the waveform panel
2. Choose **Data Format → Signed Decimal**

To view `op_code` as a named enum:

1. Right-click `op_code`
2. Choose **Data Format → Hexadecimal** (or Binary)

---

**Step 5: Use cursors to measure timing**

- **Left-click** on the waveform area to place the primary cursor (shows time at bottom)
- **Middle-click** to place a secondary cursor and measure the delta time between the two

## 8. Test Cases

The `ALU_test` coroutine in `test.py` runs the following transactions after reset:

| # | Operation | A | B | Expected Result | Expected Flags |
|---|-----------|---|---|-----------------|----------------|
| 1 | ADD | +3 | +2 | +5 | Z=0, N=0, C=0, V=0 |
| 2 | SUB | +5 | +2 | +3 | Z=0, N=0, C=1, V=0 |
| 3 | AND | +7 | +1 | +1 | Z=0, N=0, C=0, V=0 |
| 4 | OR | +4 | +1 | +5 | Z=0, N=0, C=0, V=0 |

The **Scoreboard's `reference_model()`** computes the expected values in Python and asserts them against the captured DUT outputs. Any mismatch raises an `AssertionError` and fails the test.

## 9. Understanding the Output

### Terminal Logs

| Log Level | Source | Meaning |
|-----------|--------|---------|
| `INFO` | `cocotb.ALU` | General simulation messages from the DUT handle |
| `INFO ... RESET_DONE` | `Driver` | Reset sequence completed |
| `INFO ... Monitor: Transaction(...)` | `Monitor` | A transaction was captured and logged |
| `INFO ... Scoreboard: Transaction Passed` | `Scoreboard` | DUT output matched reference model |
| `ERROR` | `Monitor` | An X/Z (unknown) signal was detected |

### results.xml

The `results.xml` file is a JUnit-compatible report:

- `tests="1"` — one test function was run (`ALU_test`)
- `failures="0"` — all assertions passed
- Any assertion error appears as a `<failure>` element with the mismatch message
